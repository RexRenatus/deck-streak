# packs/data-migration

How a data port is planned, proved and run so that nobody has to trust it (SPEC-V2-2221 /
ADR-V2-2221). Its first user is DeckStreak's import of v9's database, schema 24, into DeckStreak's
own schema. The owner's scope, verbatim: "v9's schema 24 → DeckStreak, PROVED by a parity oracle
(golden fixtures generated by running v9's own Python functions over synthetic inputs, compared to
the port)", with "dry-run, idempotency, backup before migrating (Litestream), and ROLLBACK", and
"counts before and after".

`scripts/data-migration-probe.py` is the check. It is standard-library Python 3.11+ and
vendorable, reads only the tree `--root` names, runs nothing it judges, and fetches nothing. Which
seats consume this pack is its catalog row's `consumes`, the one record of that edge
(ADR-V2-1990), so this body names none.

```
phxd pack probe --pack data-migration --root PATH --format json
```

Each row runs `python3 {skills}/../scripts/data-migration-probe.py --root {root} check <class>`
under a 60-second wall. A card shows only each row's exit, so read a red row's findings by running
its class directly: `python3 scripts/data-migration-probe.py --root PATH check <class>`.

## What composes with this pack

This pack judges the port: the plan, the oracle and the run. It never copies another pack's rows.

- The target database's own practice (its sqlx migrations, connection options, WAL, `BEGIN
  IMMEDIATE`, `STRICT`, reversible and immutable migrations, restore drills) is `ledger-sqlite`'s.
  Run it against the same root beside this pack.
- A public repository's scrub of personal data, IPs, cloud ids and chat ids is greenfield's `public`
  stage and the privacy pack's. The goldens here are synthetic by construction, and this pack checks
  that they say so.
- The release that ships the port, and a rollback of the binary, is `release-ops`'s.

## The plan: `data-migration.json`

A repository states its port in one file at its root, schema `phx.data-migration.v1`. Every key is
closed: an unknown key is a finding. Start from [the plan template](templates/data-migration.template.json).

| key | holds |
|---|---|
| `source` | `system`, the pinned `user_version`, and `schema`: the path of the source's full schema snapshot |
| `target` | `migrations`: the target's sqlx migrations directory (and optionally `database`) |
| `tool` | `path` (the tool's source), `command` (the command line a runbook uses to run it) and `apply_flag` (the long flag that makes it write) |
| `runbook` | the path of the runbook whose code blocks are the port's commands, in order |
| `tables` | one entry per source table: `source`, `action`, and for every action but `drop` a `target` (or two or more `targets` for a `split`) and a `count` rule; `drop`, `filtered` and `declared` need a `reason` |
| `oracle` | `source_commit` (the old system's 40-hex commit), `generator`, `goldens`, `consumers`, `functions`, and optionally `edge_classes` |
| `proofs` | `dry_run`, `idempotency`, `rollback`, `counts`: each `path::test_name`, a test the tree defines |

The actions and the count rules each allows:

| action | count rules |
|---|---|
| `copy` | `equal` |
| `transform` | `equal`, `filtered`, `declared` |
| `split` | `sum`, `declared` |
| `merge` | `sum`, `declared` |
| `drop` | none: a `reason` instead |

**The snapshot is the whole live schema.** Take it from the database, never from the source's
bootstrap DDL: v9 creates 58 of its 64 tables in its bootstrap and 6 only through stepped
migrations. Its first line pins the version, `PRAGMA user_version = 24;`. The SQLite shell's
`.schema` does not print that pragma, so the runbook template writes it first.

## The parity oracle

The port is proved against the old system's own behaviour, not against a reading of it.

1. **A generator runs where the old code lives.** v9's source is private and DeckStreak is public,
   so the generator runs on the owner's checkout of v9 and imports v9's functions. It calls each over
   seeded synthetic inputs and writes one golden per function, `phx.parity-golden.v1`: the
   `function`, the `source_commit`, the `generator` and its `generator_sha256`, `inputs:
   synthetic`, the `seed`, and the `cases` (`input`, `output`, and optionally `class`, `diverges`,
   `note`). Start from [the generator template](templates/generate-goldens.template.py) and
   [the golden template](templates/golden.template.json).
2. **The goldens are committed and read by the port's tests.** A Rust test reads every golden
   (`include_str!` or a walk of the directory) and compares the port's output.
3. **A changed generator means regenerated goldens.** Each golden records the generator's sha256,
   so a generator edited without a regeneration reads red.
4. **An intended difference is a decision.** A case where the port must differ from v9 (a bug not
   ported) carries `diverges: {reason, adr}`, and the ADR names the function.

The port's traps, which the inputs must cover:

- **Rounding.** Python's `round()` sends a tie to the even neighbour (`round(0.5)` is 0, `round(1.5)`
  is 2); Rust's `f64::round` sends it away from zero. Use `f64::round_ties_even` (Rust 1.77+) where
  v9 used `round()`, and give every rounding function a `tie` case.
- **Floor division and remainder.** Python's `//` floors and its `%` takes the divisor's sign;
  Rust's `/` and `%` on integers truncate toward zero. Use `div_euclid` and `rem_euclid`, and give
  every such function a `negative` case.
- **The study day.** v9's day turns over at 04:00, not midnight. Give every day-keyed function a
  `rollover` case at the boundary.
- **Non-JSON numbers.** Python's `json.dumps` writes `NaN` and `Infinity` unless
  `allow_nan=False`; RFC 8259 forbids them and serde_json refuses them. Write goldens with
  `allow_nan=False` and `sort_keys=True`.
- **Float round-trip.** serde_json's default float parsing is best-effort; its `float_roundtrip`
  feature makes f64 → JSON → f64 exact. Enable it where a test compares floats exactly.

## The run

A port runs in this order, and the runbook's code blocks say so. Start from
[the runbook template](templates/migration-runbook.template.md).

1. **Pin.** Snapshot the source's schema with its `user_version`.
2. **Dry run.** The tool without its apply flag reads, plans and prints counts, and writes nothing.
3. **Back up and verify.** Restore the source's Litestream replica to a scratch path with
   `litestream restore -o PATH -integrity-check full`, choosing the point with `litestream ltx` and
   checking it with `-dry-run` first (a restore lands only on an LTX file boundary). A local
   `VACUUM INTO` snapshot or the backup API are the other safe copies of a live database; a plain
   file copy of a live database is not one.
4. **Apply.** The tool with its apply flag, from the verified copy, opening the source read-only.
5. **Verify.** `PRAGMA integrity_check` and `PRAGMA foreign_key_check` on the target: the first does
   not find foreign-key errors. Reconcile every table's count against its rule.
6. **Re-run.** A second apply changes nothing.
7. **Cut over, or roll back.** The source was only ever read, so an aborted port discards the
   target and keeps the old system serving. After a cutover, restore the target from its replica at
   the point before the import. Pause replication with `litestream stop` before a cutover; it syncs
   and reports the final transaction id.

## The rows

Twenty rows, all `tree`-scoped. The script exits 0 when green, 1 on a finding, 2 on a usage error,
and 3 when VOID: no plan, or nothing to examine, which is never a pass. Every class prints one line
per finding and `examined N`.

Stage `plan`: 5 rows (5 blocking, 0 advisory)

| row | severity | reason | refuses when |
|---|---|---|---|
| `dm.manifest` | block | `plan-malformed` | the plan is absent (VOID), is not strict JSON, has another schema or an unknown key, pins no non-negative integer version, names a path outside the tree, lists a table twice, names an unknown action, drops a table without a reason, splits into fewer than two targets, pins no 40-hex commit, or names a proof that is not `path::test_name` |
| `dm.source-pinned` | block | `source-unpinned` | the snapshot is missing, states no `PRAGMA user_version` outside a comment, states two, or states another version than the plan; or the tool's code never reads `user_version` |
| `dm.tables-covered` | block | `table-unmapped` | a table the snapshot creates is unmapped or mapped twice, or the plan maps a table the snapshot does not create. Quoted, bracketed, schema-qualified and virtual tables are read as SQLite reads them; `sqlite_` tables, TEMP tables and FTS shadow tables are not data |
| `dm.targets-exist` | block | `target-table-missing` | a target is not a table the target's migrations leave behind, replayed in sqlx's version order and grammar: a `.down.sql` is a rollback and a file that is not `<VERSION>_<DESCRIPTION>.sql` never runs; CREATE, DROP and RENAME are followed |
| `dm.count-rules` | block | `count-rule-missing` | a migrated table states no count rule, one its action does not allow, or a `filtered` or `declared` rule with no reason |

Stage `oracle`: 7 rows (5 blocking, 2 advisory)

| row | severity | reason | refuses when |
|---|---|---|---|
| `dm.oracle-goldens` | block | `golden-malformed` | the goldens directory is missing, a golden is not strict JSON (a `NaN`, an `Infinity`, a repeated key), has another schema or an unknown key, is for an undeclared function, or has a case without an input and an output; or a declared function has no golden |
| `dm.oracle-provenance` | block | `golden-stale` | a golden names another commit or generator than the plan, records no generator digest, or records one the committed generator no longer hashes to |
| `dm.oracle-consumed` | block | `golden-unread` | a golden is named by no consumer's code (a comment does not count), or a consumer is missing or holds no test |
| `dm.oracle-synthetic` | block | `golden-not-synthetic` | a golden's inputs are not `synthetic`, or it records no integer seed |
| `dm.oracle-divergences` | block | `divergence-undecided` | a diverging case gives no reason, or cites an ADR that does not exist or never names the function |
| `dm.oracle-edge-classes` | advisory | `edge-class-uncovered` | the plan declares no edge classes, names an undeclared function, or a function's goldens have no case of a class declared for it |
| `dm.oracle-float-roundtrip` | advisory | `float-not-roundtrip` | a golden holds a float and a consumer's crate reads serde_json without `float_roundtrip` (inherited from the workspace counts) |

Stage `run`: 8 rows (7 blocking, 1 advisory)

| row | severity | reason | refuses when |
|---|---|---|---|
| `dm.dry-run-default` | block | `apply-without-dry-run` | the runbook's code never runs the tool, never runs it with the apply flag, or runs it with the flag first; or the dry-run proof is not a defined test |
| `dm.source-read-only` | block | `source-writable` | the tool's code opens its source with no read-only mode: `read_only(true)`, `mode=ro`, `immutable=1`, `SQLITE_OPEN_READONLY` or `PRAGMA query_only` (a comment and `read_only(false)` do not count) |
| `dm.backup-before-apply` | block | `apply-before-backup` | no backup precedes the first apply in the runbook's code (`VACUUM INTO`, the shell's `.backup`, SQLite's rsync tool, or `litestream restore -o`), or none of it is integrity-checked before the apply |
| `dm.integrity-after` | block | `integrity-unchecked` | neither the tool's code nor the runbook after the apply runs `integrity_check`, or neither runs `foreign_key_check` |
| `dm.idempotency-proved` | block | `rerun-unproved` | the idempotency proof names a file that does not exist or a test it does not define |
| `dm.rollback-proved` | block | `rollback-unproved` | the rollback proof is not a defined test, or the runbook has no rollback section with a command |
| `dm.counts-proved` | block | `counts-unproved` | the counts proof names a file that does not exist or a test it does not define |
| `dm.no-hot-file-copy` | advisory | `hot-file-copied` | a runbook command or a shell script under `deploy/`, `scripts/`, `tools/` or `migration/` copies a database file with `cp`, `rsync` or `scp` |

## How DeckStreak adopts this

1. Copy the templates: the plan to `data-migration.json`, the generator to
   `tools/parity-oracle/generate.py`, the runbook to `docs/runbooks/v9-import.md`.
2. Write the snapshot with the runbook's first command, and list all 64 of v9's tables in `tables`.
3. Run the generator on the v9 checkout, commit the goldens, and write the port's parity tests to
   read them, with the four proof tests the plan names.
4. Run this pack and `ledger-sqlite` against the tree until both are green, then run the port by
   the runbook.
