# One allow-listed FFI adapter, an exactly pinned UniFFI, and a macOS XCFramework job

## Context and Problem Statement

SPEC-336 asks whether an iPhone and iPad client can call the engine, Anki's engine through the fork
ADR-058 pins, through one FFI crate packaged as an arm64 XCFramework with a device slice and a
simulator slice, built in CI. The engine's own clients already speak one shape: a backend service's
index, a method's index and the request's protobuf bytes go in, and the response's bytes come out
(`Backend::run_service_method`). Amgi (github.com/antigluten/amgi) carries that shape through a
four-function C FFI into the same call.

Six things had to be decided: where the FFI surface lives, which bindings generator and version it
is built with, how the generator is run, where the framework is built, how a default-feature test
reaches the generator's binary, and how the settle census (SPEC-072, ADR-197), which refused every
member that declares a feature because it compiled none, judges the adapter's `bindgen` feature.

## Decision Drivers

- The crate graph is the context map: the FFI surface must add no edge into a context.
- A native client must reach only the calls it is allowed, and a refused call must never panic.
- The Swift bindings must be generated by the version the library links, or the bindings and the
  scaffolding can disagree.
- Apple's SDKs exist only on a macOS runner, and the workflow hardening test admits pinned Ubuntu
  images alone.
- A workspace build that does not need the generator or a static library must not pay for either.
- The pull request's mutation run passes no feature, so every mutant cargo-mutants lists in the
  adapter must be built, and caught, by a default-feature test.
- The settle census guards progression's own invariant, that only coordination settles, over every
  member. A change to it must refuse every shape it refused before that hides a call, and may
  admit a member only because its code under every feature was compiled and found clean.

## Considered Options (the alternatives it was chosen against)

- D1, one adapter crate, `deck-streak-ffi`, at the edge, depending on the engine alone - chosen,
  because it adds no edge into a context and holds the whole surface in one allow-list.
- D1, a module inside `deck-streak-ingest` - lost: it would put the FFI surface inside a bounded
  context, and the context's other code would be one import away from the client's boundary.
- D1, one crate per exposed context - lost: not admitted for this spike, and the five calls are all
  the engine's, so there is no second context to expose.
- D2, `uniffi = "=0.29.1"` - chosen, because it is the last release whose generated Swift
  modulemap names no builtin clang module and it supports the 2024 edition the workspace builds in.
- D2, `uniffi` 0.29.2 or later - lost: from 0.29.2 the modulemap template adds `use "Darwin"`,
  `use "_Builtin_stdbool"` and `use "_Builtin_stdint"` (mozilla/uniffi-rs#2506), the shape
  mozilla/uniffi-rs#2917 reports breaking a simulator XCFramework's consumers. That issue is open
  with no fix, and maintainers there report that they cannot reproduce it, so the pin is a
  precaution whose cost is staying on an older release; the workflow's modulemap check and consumer
  check measure the shape on every run.
- D2, `uniffi` 0.28 - lost: it predates the 2024 edition support 0.29.1 records in its changelog.
- D3, the generator as the adapter's own binary, built only with its `bindgen` feature - chosen,
  because the generator then comes from the exact bindings crate the library links.
- D3, `cargo install` of a separate generator - lost: its version is fixed by the install line, not
  by the lockfile, and can drift from the scaffolding the library links.
- D3, a second crate holding the generator - lost: not admitted for this spike, which admits one
  new crate.
- D4, a workflow of its own on a macOS runner - chosen, because only the XCFramework build then
  pays for a static library of the engine, which it builds per target with
  `cargo rustc --crate-type staticlib`.
- D4, `crate-type = ["staticlib"]` in the adapter's manifest - lost: every host build of the
  workspace would then link a static library of the whole engine.
- D4, admitting macOS runners by pattern in the hardening test - lost: a pattern admits the runner
  to every workflow, so the admission is by this workflow's file name and refuses the runner
  under any other name.
- D5, the generator's binary in every build, refusing without `bindgen` - chosen, because the
  default-feature mutation run then builds the binary and A8 catches the mutant that empties its
  `main` (row S33601), while the generator's code stays behind the feature: a build without it
  gains one binary that only prints a refusal and exits 2.
- D5, a test that runs a nested `cargo run --features bindgen` of the generator - lost: measured
  after the crate's default test build, it compiled 42 more crates, the engine among them,
  because the feature changes shared dependencies' feature sets, and every CI job and mutation
  shard that tests the crate would pay that second build.
- D5, the generator moved to `examples/` with its required feature - lost: cargo-mutants lists no
  example, so the mutant leaves the population (9 mutants listed against 10), which is a skip,
  not a kill.
- D5, the mutation run given `--features bindgen` - lost: a change to the shared mutation
  configuration for one binary's mutant, and every crate's mutation run would build under a
  feature only this adapter declares.
- D6, the census compiles every combination of the members' features - chosen, because every build
  a member's features allow is then compiled in some pass: it reads the graph with every feature
  on, compiles each combination with each member's default off unless the combination holds it,
  and refuses a feature another package turns on and a fourth feature, so a call under a feature,
  under its absence or under any mix is refused for the call, and the adapter is admitted only
  after its code under `bindgen` is compiled and found clean. It lives in progression's test
  because the invariant is progression's, and it adds no dependency edge.
- D6, admitting the adapter by name - lost: the census would carry another context's name and
  skip whatever code that crate holds under a feature, a weakening for every later change to it.
- D6, dropping the adapter's `bindgen` feature - lost: D3 and D5 rest on it, and the generator
  would then be built in every build of the workspace.
- D6, the generator in a crate of its own - lost: D3 rejected a second crate for this spike, and
  the census would still refuse that crate's feature.
- D6, one more pass with `--all-features` only - lost: code under a feature's absence, such as
  `cfg(not(feature = "x"))` beside a default feature, is compiled in no pass.
- D6, one pass per feature, each alone - lost: code under two features together, or under one
  feature and another's absence, is compiled in no pass.
- D6, one `-p` build per member - lost: a member's code that a dependent's feature request
  changes, and a macro another member expands, are compiled only as the workspace build compiles
  them, and the passes then differ from the workspace build the census reads.

## Decision Outcome

Chosen options: D1 one adapter crate depending on the engine alone, D2 the exact pin, D3 the
generator behind the adapter's `bindgen` feature, D4 the macOS job admitted by file name, D5
a generator binary that every build compiles and that refuses without the feature, and D6 a
settle census that compiles every combination of the declared features, because together they
keep the FFI surface out of every context, generate the bindings from the version the library
links, charge the static library and the generator to the one workflow that needs them, leave no
mutant of the adapter outside the default-feature tests, and leave no code under a feature unseen
by the census.

### Consequences

- Good, because the context map gains a line with no internal edge, and the ddd probe holds the
  manifest equal to it.
- Good, because a refused call is a typed error a Swift caller catches, and the allow-list decides
  before the engine sees the call.
- Bad, because the bindings crate's internal macros crate is reached through a non-exact
  requirement, so the lockfile, not the pin, fixes its version (it resolves to 0.29.5); the
  lockfile check and `cargo deny` hold it.
- Good, because the mutation run builds the generator's binary, and A8 catches cargo-mutants'
  mutant of its `main`, which row S33601 also installs by hand.
- Bad, because every build of the adapter now compiles and links one more binary, and no host test
  runs the generator built with the feature; the workflow's bindings step runs it on every pull
  request that changes the adapter.
- Bad, because the macOS protobuf compiler's digest is Anki's own pin for that archive, and the
  hardening test's protoc guard reads only the Linux pin; the job's checksum step fails on a
  mismatch, but no test compares the two pins.
- Good, because the census now refuses a call to `settle` under any combination of features for
  the call itself, where before it refused the feature and never compiled the code beneath it.
- Bad, because each declared feature doubles the census's compiles of the workspace, so the census
  refuses a fourth feature by name, and raising that bound is a reviewed change.
- Bad, because a member whose feature another package turns on is refused outright, though its
  code might be clean: the census cannot compile it without the feature, as a build of that member
  alone does.

### Confirmation

SPEC-336 A1 to A6 round-trip each allowed call and refuse unlisted ones on a synthetic collection;
A7 holds the runner admission; A8 holds the generator's refusal without its feature, and row
S33601 proves it kills the empty `main`; `refusal_text` holds each refusal's text. A9 to A12 hold
the census's combinations, its graph and its two refusals, each beside a control, and the rows
from S33602 prove each part of the change is observed; A13 and A14 judge the real tree. The workflow fails on a
builtin clang module in the modulemap and on generated Swift that does not typecheck against either
slice's headers. `cargo deny` and the lockfile check hold the pin.

## Amendment: the census leaves out the Kani witness features by name, behind a reach guard (ADR-531 D7, ADR-527 D7)

This amends D6 (`:82-88`) and its rejected option of admitting by name (`:89-90`), for the Kani
witness features alone. The rest of D6 stands.

- **Why.** ADR-531 D7 gave the media crate four Kani mutation-witness features
  (`kani-witness-blob-path`, `-bind`, `-sweep` and `-scan`), and ADR-527 D7 gave the sync crate
  four (`kani-witness-sync-codec-len`, `-key-order-noseq`, `-hlc-plain-add` and
  `-next-id-residue`). With the adapter's `bindgen` the members then declared nine features, past
  the three whose every combination D6 compiles, and the census refused the real tree by name
  (SPEC-336 R11). Nine features would be 512 combinations for each selection in each pass, where
  the census now compiles 2.
- **What changes.** The census holds a closed list of the witness features, `WITNESSES` in
  `crates/progression/tests/xp_census.rs`, each named by its package and its feature and never by
  a pattern. A listed feature is left out of the combinations only while no package that reaches
  progression, progression among them, reaches the feature's crate, that crate among them. The
  census reads this from the graph with every feature on, on every run, and prints how many
  features it left out and which. A listed feature that fails the check is counted and compiled as
  any feature is.
- **Why D6's guarded property holds.** D6 guards that no code under a feature, under its absence
  or under any mix of features calls `settle` outside coordination, and the same census holds that
  no code outside progression names `xp_settlement` (SPEC-072 A12). A call to progression's
  `settle` compiles only in a crate that reaches progression, and a macro the witness's crate
  exports is expanded only in a crate that depends on it. While no package reaches both
  progression and the witness's crate, neither that crate's own code nor any expansion of its
  macros can call `settle`, with the feature on or off. The table's name is read as text from
  every file of every member's `src` and from every migration, whatever the features, so a
  feature left out of the compiles hides no writer of `xp_settlement` from that reader. The
  guard is read on every run, so a later change that gives a witness's crate a path to progression
  puts the witness back in the combinations, where a call under it is refused for the call. The
  rejected option skipped a named crate's code whatever the graph held; the list skips a named
  feature only while the graph shows that no code under it can be such a use, which is why it is
  not the weakening D6 refused.
- **What stays.** Every feature the list does not name is counted and compiled: a plain feature,
  one named like a witness but not listed, and a listed name in another package alike. A fourth
  feature that is not a left-out witness is still refused by name, and a feature another package
  turns on is still refused, a listed witness among them, as D6 decided. The test
  `a_kani_witness_is_left_out_by_its_name_and_only_apart_from_settle` holds both sides, each beside
  its control, and row S33611 still holds the bound at three.
- **The noted risk.** A witness feature is not `cfg(kani)` code: each switches the body of a
  shipped function to its recorded defect (media's `bind.rs`, `hash.rs`, `sweep.rs` and `scan.rs`;
  sync's `ids.rs`, `codec.rs`, `key.rs` and `clock.rs`), and a build that turned one on would ship
  that defect. No build may turn one on; the formal check's witness run is the only use ADR-527 D7
  and ADR-531 D7 give them. The census does not judge that: it asks only whether code under a
  feature can call `settle` or name `xp_settlement`, never whether a shipped build turns a witness
  on.

- Chosen: the closed list behind the reach guard, because the census then still compiles every
  feature whose code can reach `settle`, and its combinations stay those of the other features.
- Raising the bound to nine: rejected because each selection in each pass would then compile 512
  combinations where it compiles 2, and SPEC-336 R11 and row S33611 hold the bound at three.
- Admitting the media and sync crates by name: rejected for the reason D6 gave, since every later
  feature of either crate would then be skipped whatever it reached.
- Dropping the witness features: rejected because ADR-527 D7 and ADR-531 D7 rest on them, and a
  harness with no witness cannot fail.
