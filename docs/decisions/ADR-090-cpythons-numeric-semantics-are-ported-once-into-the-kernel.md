# CPython's numeric semantics are ported once, into the kernel

## Context and Problem Statement

W4's ports read the predecessor's numbers through CPython's own arithmetic (predecessor `27ee2bc`):
the built-in `sum` (compensated since CPython 3.12), `statistics.median`, `statistics.mean` (the
exact mean, rounded once), `round(x, n)`, the nearest-rank percentile of
`gamification/adaptive.py:percentile`, the Mersenne Twister behind `random.Random` (seeding,
`random()`, unweighted `choices`, `shuffle`), `math.lgamma` and `math.erfc`. Each differs from a
naive Rust expression at an edge: a running float sum is not the compensated one, an even median
averages the two middle values, `round(x, n)` rounds the float's exact binary value, half to even only on an exact tie, so `round(2.675, 2)` is 2.67, and a generator
consumed in another order draws other numbers. SPEC-071 already holds a compensated sum in
analytics. Where do these semantics live, so that curriculum, insights and analytics all read the
same ones?

## Decision Drivers

- ADR-012: every number is proved against a golden of the predecessor's own function; an edge the
  port gets wrong fails a golden far from its cause.
- ADR-002: contexts may not depend on each other; a primitive several of them read belongs in the
  shared kernel, which knows no context.
- The primitives are arithmetic, not rules: none of them names a card, a course or a reward.

## Considered Options (the alternatives it was chosen against)

- One module, `crates/kernel/src/pynum.rs`, each function proved by a CPython golden — chosen: one copy for every context, its edges proved once, and the kernel stays free of domain rules because these are arithmetic.
- A copy in each crate that needs one — rejected because two copies drift silently, and a fix proved in one context stays wrong in the other.
- A new crate outside the context map — rejected because it adds an edge to every consuming crate for what the shared kernel already exists to hold.
- Rust's plain float operations — rejected because they differ from CPython at exactly the edges the goldens hold (compensation, even medians, half-even rounding, the exact mean).
- Calling Python at run time — rejected because it adds an interpreter to the service for a few hundred lines of arithmetic.

## Decision Outcome

Chosen option: "One module in the kernel", because the semantics are shared arithmetic that every
consuming context must read identically.

- SPEC-090 adds `sum`, `median`, `mean`, `round` and the percentile; SPEC-095 the generator
  (seeding, `random()`, unweighted `choices`) and `lgamma`; SPEC-097 `shuffle` and `erfc`.
- Each function equals a golden generated by CPython over edge cases; analytics' compensated sum
  (SPEC-071) delegates to the kernel's and keeps its own name.
- A function joins `pynum` only when a ported rule reads it; the module is not a general numeric
  library.

### Consequences

- Good, because a numeric edge is fixed once and every context inherits the fix.
- Good, because the goldens name CPython's behaviour, so a reader sees why a line is not the
  obvious Rust.
- Bad, because the kernel grows with each wave that ports a new CPython primitive; the rule above
  keeps it to what a port reads.

### Confirmation

SPEC-090's A1 and A2, SPEC-095's generator criteria and SPEC-097's A1, each over its CPython golden,
and the mutation rows that target `crates/kernel/src/pynum.rs`.

## What would make this wrong

- A context needs a primitive whose semantics depend on its own rules; that belongs in the context.
- A later toolchain gives the same semantics from a maintained crate; the module then delegates to
  it and keeps its goldens.
