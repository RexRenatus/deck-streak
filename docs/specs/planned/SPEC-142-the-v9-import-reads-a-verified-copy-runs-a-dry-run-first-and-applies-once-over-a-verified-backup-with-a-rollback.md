# SPEC-142: the v9 import reads a verified copy, runs a dry run first, and applies once over a verified backup with a rollback

- **Wave:** W8. **Issue:** #61 (epic #9), its first criterion (the data-migration pack's rows over
  `data-migration.json`) and its second (counts reconcile per table, and a second apply changes
  nothing). **Context(s):** `deck-streak-migration` (new: the copy reader, the plan, the
  composition of every owner's import port, the reconcile, the backup check and the rollback),
  `deck-streak-daemon` (the `import` role), the repository (`data-migration.json`) and `deploy`
  (the runbook).
- **Decided by:** ADR-008 (the v9 import follows `data-migration.json`), ADR-011 (the import runs
  last, from a verified backup), ADR-012 (the parity oracle proves the math), ADR-140 (each owner
  writes its own imported rows, in one transaction) and ADR-142 (the dry run rehearses on a copy of
  DeckStreak's database, and the one apply stands on a Litestream restore verified as its backup).
- **Prerequisites:** SPEC-020, SPEC-021, SPEC-029 and SPEC-064 (landed); SPEC-140 and SPEC-141 (this
  wave, unlanded), and through them every SPEC whose migration creates a table the plan targets
  (their Prerequisites lines). **Mutation band:** `S14200-S14299`.
- **Status:** planned (in `docs/specs/planned/`) until the delivery that builds it moves it to
  `docs/specs/` with its tests and `docs/red-first/SPEC-142.md` (ADR-016).

## 1. The problem, measured

- **Nothing composes the owners' writers.** SPEC-140 and SPEC-141 give each owner an `ImportPort`
  that writes its own tables inside a transaction its caller holds, and answers one count per pair
  of source and target table. At `dev` a4036b3 `docs/CONTEXT-MAP.md` names `deck-streak-migration`
  as PLANNED with no code, and no role of `deckstreakd` (`crates/daemon/src/main.rs`: `api`, `bot`,
  `job`, `data`) can run an import.
- **There is no plan for the data-migration pack to judge.** `data-migration.json` does not exist,
  so the pack's rows, #61's first criterion, have nothing to read; the pack is not yet enforced,
  and #61 is the issue that enforces it. The predecessor's schema at `27ee2bc` creates 64 persisted
  tables at `user_version = 24` (`database.py`: `SCHEMA_VERSION = 24`).
- **The pieces a safe run needs exist, apart.** The kernel opens another program's file read-only
  (`Db::open_foreign_read_only`: `mode=ro` and `query_only`, SPEC-020 R17), and writes go through
  `Db::write`'s `BEGIN IMMEDIATE` (R16). The restore drill (SPEC-064 R5) already restores the
  replica with `litestream restore -config <configuration> -o <path> <database>` and checks the
  result with `PRAGMA integrity_check` through Python's standard library.
- **Two accepted records fix the order.** ADR-008 asks for "a dry run, a Litestream restore
  verified before the apply, integrity and foreign-key checks after, and a rollback that discards
  the target while v9 keeps serving"; ADR-011 runs the import last, after the checklist's moves,
  from a verified backup. ADR-142 reads the two together: the dry run is the rehearsal that
  discards its target while the predecessor keeps its own, and the one apply comes after the go.

## 2. Requirements

The copy

R1. `crates/migration` (the crate `deck-streak-migration`) reads a COPY of the predecessor's
    database, named by `--source <file>` with its digest `--sha256 <hex>`, which the private rail
    (#41) delivers; nothing in the repository names where the predecessor keeps its database.
    Before it reads a row it refuses, each by its reason: a copy whose sha256 differs from the one
    given; a copy with a non-empty `-wal` file beside it (a copy of a file in use rather than a
    backup); a `PRAGMA user_version` other than 24; and a set of tables other than the snapshot's
    (R2). It opens the copy only through `Db::open_foreign_read_only`, reads it on one connection
    inside one read transaction, on which it first states `PRAGMA query_only = ON` again, and loads
    SPEC-140's `SourceTables`.
R2. The snapshot `crates/migration/v9/schema-24.sql` holds the predecessor's CREATE statements at
    `27ee2bc` and no row, beginning with `PRAGMA user_version = 24;`. It is generated by
    `tools/parity-oracle/migration/generate.py --schema`, which has the predecessor's own store
    create its schema in a temporary file and writes that file's `sqlite_schema` SQL; it is never
    typed by hand.

The plan

R3. `data-migration.json` at the repository's root is the plan, in the data-migration pack's shape
    (`phx.data-migration.v1`): `source` (the snapshot, `user_version` 24), `target` (`migrations`,
    the database `deck_streak.db`), `tool` (`crates/migration`, the command `deckstreakd import`,
    the apply flag `--apply`), the runbook `deploy/v9-import.md`, the 64 source tables as §8 maps
    them (49 transformed, 7 split, 8 dropped, each drop with its reason), `oracle` (the source
    commit `27ee2bc` in full, SPEC-140 §7's generator and folder, the three test files that read
    the goldens, the seven functions of SPEC-140 §7 and SPEC-141 §7, and for each function the case
    classes its SPEC's §7 row lists as its edge classes), and `proofs` (the dry run A6, the
    idempotency A10, the rollback A12 and the counts A13).
R4. `crates/migration/v9/settings-keys.json` names every key family of the predecessor's settings
    that no owner's family takes (SPEC-141 R7), each with its reason and issue: the art counters
    and model (#125), the money rung's four keys (ADR-106, #116), the tripwire's channel (#170),
    the ingest base and the sync gate's two anchors (SPEC-022, SPEC-023: DeckStreak keeps its own),
    the publishing baseline (#348), and the three side-by-side switches, which the checklist reads
    (SPEC-143). A source key that neither an owner's family nor this file names refuses the plan by
    its key, never its value.

The run

R5. `deckstreakd import --source <copy> --sha256 <hex>`, without `--apply`, is the dry run: it
    opens DeckStreak's database, copies it with `VACUUM INTO` into a new file in a private
    temporary directory, runs R7's apply on that copy, runs it a second time (every pair must answer
    `unchanged`, with `written` 0), runs `PRAGMA integrity_check` and `PRAGMA foreign_key_check` on
    the copy, prints the report (R10), and removes the copy. It writes nothing to DeckStreak's
    database, so it can run side by side (#62) before the owner's go, and it waits on nothing.
R6. `deckstreakd import --apply --source <copy> --sha256 <hex> --backup <file>` refuses without
    `--backup`, and refuses a backup whose `PRAGMA integrity_check` answers anything but `ok`, or
    whose tables differ from the live database's: a sha256 per table over its rows in primary-key
    order, taken of the live database inside the apply's own write transaction, so no write can
    fall between the comparison and the apply.
R7. The apply is one `Db::write` transaction in which the composition calls every owner's
    `ImportPort::write` (SPEC-140 R1) in §8's order, a table after the tables its foreign keys name,
    and hands vault the drill XP map that progression's `import::drill_xp` reads (SPEC-140 R13).
    Any refusal (SPEC-140 R14, R4 here) or a reconcile that differs (R9) rolls the whole
    transaction back, and nothing is written.
R8. After the commit the apply runs `PRAGMA integrity_check` and `PRAGMA foreign_key_check` on the
    live database. Anything but `ok` and no row fails the run with exit code 1 and prints the
    rollback's command line (R11). The apply writes nothing of its own, and every instant it writes
    comes from the source (SPEC-140 R4), so a second apply of the same copy answers every pair
    `unchanged` with `written` 0.
R9. The reconcile judges each source table under its plan rule: `equal`, the source's rows equal
    `inserted + replaced + unchanged`; `filtered`, they equal that plus `filtered` (SPEC-140 R1);
    `sum`, a split's source rows equal the sum of its pairs' taken rows, each row taken once;
    `declared`, the counts are printed beside the plan's reason, and for the settings table every
    source key is taken by exactly one owner's family or named by R4's file (the cross-owner sum
    SPEC-141 R10 leaves here). The ledger also reconciles its XP: the imported XP of `xp_ledger` and
    `xp_settlement` together equals the source's, and SPEC-140's `day_base_xp` equals the source's
    for every study day. `kept` and `superseded` count DeckStreak's own rows and enter no rule; the
    report shows them.
R10. The report is one line per source table, `table=<name> action=<action> rule=<rule>
    source=<n> taken=<n> inserted=<n> replaced=<n> unchanged=<n> filtered=<n> superseded=<n>
    kept=<n> verdict=<reconciled|declared|differs>`, then SPEC-140's `unstamped` count, then one of
    `IMPORT PLAN OK`, `IMPORT PLAN REFUSED: <n>`, `IMPORT APPLIED` or `IMPORT REFUSED: <n>`. A
    refusal names the table, the column or key and the reason, and never a row's value. The
    owner's recorded report holds counts of personal data and stays private.
R11. `deckstreakd import rollback --backup <file>` restores the backup. Before it renames anything
    it refuses, each by its reason with exit code 1: a backup that is not a file in the live
    database's own directory (a rename across filesystems fails after the live file has moved
    aside, leaving no database at the live name); a `.failed-import` name already taken (a second
    rollback would replace the file the first one kept); and a backup whose `PRAGMA
    integrity_check` is not `ok`. It then renames the live file and its `-wal` and `-shm` aside
    with the suffix `.failed-import` (kept for the owner, never deleted or replaced by the tool),
    renames the backup to the live name, syncs the directory, and checks the result with `PRAGMA
    integrity_check`; a result that is not `ok` exits 1 naming both files, and keeps both. It
    copies no file.
R12. `crates/daemon/src/role_import.rs` runs the role: `Role::Import(ImportCommand)`, `NAMES`
    gains `import`, and the database is the one the other roles open from `STATE_DIRECTORY`. Its
    exit codes are 0 (reconciled, applied, rolled back), 1 (refused, differs, or a fault after the
    apply) and the house `USAGE` 2 (arguments it does not take). No job, timer, route or command
    of the bot runs it: the import runs by hand, from the runbook, once.
R13. The runbook `deploy/v9-import.md` gives the order, each step a command in a code block:
    the dry run, as often as the owner likes before the go; then, after the owner's go (#164),
    after the checklist's last move (SPEC-143) and after the predecessor stops (the private rail,
    #41): the dry run of the final copy; DeckStreak's writers stopped (the API, the bot, the job
    timers and the path unit; the Litestream daemon keeps running); the backup, `litestream restore
    -config <DeckStreak's configuration> -o <backup> <database>` with `<backup>` a new file in the
    database's own directory, and `PRAGMA integrity_check` on the restored file through Python's
    standard library, read-only, as the restore drill does (SPEC-064 R5); the apply (a backup it
    refuses as different, R6, is restored again after the daemon's next sync); the writers
    started. A `## Rollback` section stops the Litestream daemon, runs R11, resets Litestream's
    local tracking for the replaced file as its documentation directs for a replaced database, and
    starts the daemon and the writers; it gives each of R11's refusals and its failure a reply: a
    backup outside the directory is restored again into it, a taken `.failed-import` name is moved
    by the owner to a name of their choosing, and a backup or a result that fails its check is
    restored again from the replica at the point before the import, each followed by R11 again,
    with the writers still stopped. It copies no database
    file with `cp`, `rsync` or `scp`, and every step after the dry run names #164 as its gate. The
    builder confirms each Litestream subcommand it names against the version the private rail
    records (SPEC-064 R1), with Context7.
R14. `docs/CONTEXT-MAP.md`: the migration crate's line gives its built edges (kernel, ingest,
    analytics, progression, streaks, curriculum, economy, quests, habits, focus, discipline,
    markets, notifications, readings, vault and publishing: ingest's skipped days and publishing's
    state are written by their owners' ports too), the daemon's line gains `migration`, and the
    PLANNED note keeps only `landing`.
R15. CHARTER 10's eleven anti-goals bind this SPEC as one block; the ones it touches are no
    fabricated history (the import carries only what the predecessor recorded, and a count it
    never read arrives NULL, SPEC-140 R7) and no unbounded faucet (the import grants, settles,
    mints and raises nothing, SPEC-140 R5, and A20 proves it through the first recompute after).

## 5. What this does NOT do

- It moves no side-by-side switch and no vault contract; the checklist does, one at a time
  (#62).
- It stops, disables and removes nothing of the predecessor; the private rail carries that out on
  the owner's go (#41, #164).
- It adds no job, timer, route or bot command: the import runs by hand, once, from the runbook
  (#63).
- It carries none of R4's keys (#125, #116, #170, #348).
- It restores no replica over the live file: the rollback restores the backup the runbook made
  before the apply (#61).
- It changes no repository setting and tags no release (#64).

## 6. Risks

- **A hot copy read as a backup**, with its last writes in a journal beside it. Prevented by R1's
  journal and digest refusals, and detected by A1, A3 and rows S14201 and S14203.
- **The source written by the import.** Prevented by the kernel's read-only open and R1's
  `query_only`, and detected by A5 and row S14205.
- **A dry run that writes the live database.** Prevented by R5's copy, and detected by A6 and row
  S14206.
- **A backup that is not the state the apply changed**, so a rollback would lose a write. Prevented
  by R6's per-table digests inside the write transaction, and detected by A8 and row S14208.
- **A partial import** after one writer refuses. Prevented by R7's one transaction, and detected by
  A9 and row S14209.
- **A count that drifts unseen.** Prevented by R9, and detected by A13, A14 and rows S14212 and
  S14213.
- **A rollback that replays the failed apply's journal** into the restored file. Prevented by R11's
  renaming of `-wal` and `-shm` aside, and detected by A12 and row S14211.
- **A personal value in a public record.** Prevented by R10, and detected by A19 and row S14215.
- **The Litestream replica behind the live file** when the backup is restored. Detected by R6's
  digests, which refuse the apply; the runbook waits for the daemon's sync and restores again.

## 8. Tables and the v9 import

This SPEC adds no table. It is the census #61 collects: every DeckStreak table, the SPEC that
creates it, the predecessor table it maps from, and its rule. The plan's order is this table's.
"equal", "filtered", "sum" and "declared" are the plan's count rules; "derived" is recomputed and
not imported; "not carried" is DeckStreak's own and starts empty; "empty" has no predecessor
table.

|---|---|---|---|
| `_sqlx_migrations` | kernel (sqlx) | `schema_versions` | exempt: the source's `user_version` is checked instead (dropped) |
| `settings_generation` | kernel (SPEC-020) | nothing | derived |
| `daily_rollup`, `daily_lang_stats` | analytics (SPEC-071) | the tables of those names | equal |
